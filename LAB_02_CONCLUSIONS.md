# Отчет и выводы по Лабораторной работе №2

## 1. Цель работы
Перевести чат-агента **AI Mock Interviewer** на современный стек **LangChain (LCEL)**, внедрить долговременную память фактов на базе JSON-файла и вынести служебную информацию в отдельный изолированный блок вывода (кастомную ячейку — CELL).

**Ключевые задачи:**
1. Собрать конвейер обработки на LangChain Expression Language (LCEL).
2. Реализовать компонент памяти фактов (`FileFactMemory`), сохраняющий структурированные данные о кандидате и прогрессе вопросов в `memory.json`.
3. Реализовать кастомную ячейку (`CustomInterviewCell`) для вывода метаданных (оценки, статус синхронизации) отдельно от реплик интервьюера.
4. Обеспечить сохранение состояния при перезапуске: агент не должен повторно задавать уже отвеченные вопросы.

---

## 2. Архитектура решения и используемый стек
* **Фреймворк:** `LangChain 1.4+` (`langchain-core`, `langchain-openai`).
* **Локальный инференс:** `llama-server` (OpenAI-совместимый API, Apple M1, Metal GPU).
* **Модели:** `Qwen 2.5 3B Instruct` / `Llama 3.2 3B Instruct`.
* **Файловая структура работы:**
  * `interview_agent_v2.py` — основной исполняемый скрипт агента.
  * `memory.json` — персистентное хранилище фактов и очереди вопросов.
  * `LAB_02_CONCLUSIONS.md` — отчет о результатах выполнения работы.

### Конвейер обработки (LCEL Chain)
Вместо ручного разбора строк и циклов запросов, как в первой работе, применен декларативный конвейер:
```text
Входные данные (память + вопрос + ответ)
   │
   ▼
ChatPromptTemplate (системный промпт с контекстом памяти)
   │
   ▼
ChatOpenAI (локальная модель через llama-server)
   │
   ▼
StrOutputParser (извлечение текста)
   │
   ▼
CustomInterviewCell (сервисный блок вывода и обновление memory.json)
```

## 3. Долговременная память фактов (FileFactMemory)
В соответствии с требованиями задания, память разделена на два понятия:
* **История сообщений (Chat History):** в этой работе намеренно **не сохраняется** на диск целиком, чтобы не раздувать контекст модели и не тратить оперативную память.
* **Память фактов (Fact Memory):** сохраняет только структурированную выжимку о пользователе:
  1. Профиль кандидата: имя, целевая позиция, ключевые навыки.
  2. Очередь запланированных вопросов (`pending_questions`).
  3. Результаты пройденных тем (`completed_questions`): тема, выставленный балл (от 1 до 10), комментарий интервьюера и дата ответа.

При запуске класс `FileFactMemory` считывает `memory.json`. Если файл отсутствует, он автоматически создает шаблон по умолчанию.

## 4. Собственная ячейка вывода (CustomInterviewCell)
Преподаватель указал в задании: *«служебную информацию нужно выводить через собственную CELL (отдельный блок вывода), а не в основной чат»*.

Для решения этой задачи создан класс `CustomInterviewCell`, являющийся наследником `Runnable`:
* Он принимает ответ от модели и анализирует его.
* Оценка кандидата и технический комментарий извлекаются и оформляются в виде визуального сервисного блока.
* В диалоговом окне реплика интервьюера и служебный блок не перемешиваются, что делает интерфейс чистым и профессиональным.
* Ячейка автоматически вызывает сохранение актуализированных данных в `memory.json`.

## 5. Демонстрация работы и проверка перезапуска

### Сессия 1: Первый запуск и прохождение вопроса
При запуске агент приветствует кандидата по имени из памяти («Виктор») и задает первый вопрос из очереди:
> **Интервьюер:** *«Как устроен GIL (Global Interpreter Lock) в CPython? В каких задачах он становится узким местом, а когда не влияет на производительность?»*

Кандидат отправляет развернутый ответ про CPU-bound и I/O-bound задачи.

**Срабатывание Custom CELL (сервисный блок):**
```text
┌────────────────────────────────────────────────────────────────────────┐
│  📊 СЕРВИСНЫЙ БЛОК ЯЧЕЙКИ (CUSTOM INTERVIEW CELL)                       │
├────────────────────────────────────────────────────────────────────────┤
│  Тема:             Python Core (gil_threading)                          │
│  Оценка:           8/10                                                 │
│  Комментарий:      Отличный ответ. Корректно описаны CPU-bound задачи  │
│                    и поведение GIL при операциях ввода-вывода.          │
│  Статус памяти:    ✅ Успешно синхронизировано с memory.json            │
└────────────────────────────────────────────────────────────────────────┘
```

После этого пользователь вводит команду `выход`.

### Проверка состояния файла `memory.json`
После завершения первой сессии файл `memory.json` автоматически обновился:
* Вопрос `gil_threading` удален из списка `pending_questions`.
* В секцию `completed_questions` добавлена запись:
```json
"gil_threading": {
  "topic": "Python Core",
  "score": 8,
  "feedback": "Отличный ответ. Корректно описаны CPU-bound задачи...",
  "completed_at": "2026-10-16 00:15:30"
}
```

### Сессия 2: Перезапуск с сохранением памяти (ключевой тест)
Скрипт запускается заново с чистым процессом Python:
```bash
python3 interview_agent_v2.py
```

**Поведение агента:**
1. Агент считывает `memory.json` с диска.
2. Проверяет словарь `completed_questions` и видит, что тема `gil_threading` уже закрыта с оценкой 8/10.
3. Агент **не задает вопрос по GIL повторно**.
4. Собеседование сразу продолжается со следующего нерешенного вопроса:
> **Интервьюер:** *«В чем разница между WHERE и HAVING в SQL? Почему поиск по условию LIKE '%abc' не может эффективно использовать B-Tree индекс?»*

Тем самым требование непрерывности сессий при перезапуске полностью подтверждено.

## 6. Сравнение подходов (Лабораторная 1 vs Лабораторная 2)

| Критерий | Лабораторная №1 (Чистый Python) | Лабораторная №2 (LangChain + Память) |
| :--- | :--- | :--- |
| **Организация логики** | Циклы `while`, ручные вызовы `requests` | Цепочки LCEL (`prompt \| llm \| cell`) |
| **Вызов инструментов** | Текстовый парсинг `$call$...$call$` | Структурированная обработка через ячейки |
| **Сохранение состояния** | Только текстовые логи, состояние терялось | Персистентный `memory.json` |
| **Перезапуск сессии** | Начиналось заново с первого вопроса | Продолжение ровно с места остановки |
| **Разделение вывода** | Все выводилось в общий поток консоли | Служебные данные изолированы в Custom CELL |

## 7. Итоговые выводы
1. **Эффективность LCEL:** Использование LangChain Expression Language позволило сократить объем служебного кода и сделать конвейер агента модульным и легко расширяемым.
2. **Надежность памяти фактов:** Хранение выжимки знаний вместо полного контекста сообщений экономит память графического ускорителя (GPU/Metal) и предотвращает зацикливание модели на истории предыдущих реплик.
