# Отчет и выводы по Лабораторной работе №3

## 1. Цель работы
Расширить функциональность агента **AI Mock Interviewer** на базе материалов **Занятия 04** (типы памяти в LangChain и условные цепочки `RunnableBranch`) и **Занятия 05** (механика инструментов `@tool`, схемы аргументов и диспетчеризация вызовов).

**Ключевые задачи:**
1. Внедрить комбинированную систему памяти: оконную память последних реплик (`BufferWindowMemory`), суммаризирующую память (`SummaryMemory`) и файловую память фактов (`memory_v3.json`) с хранением текущего уровня знаний кандидата (`junior` / `middle` / `senior`).
2. Разработать кастомный `Runnable`-компонент с разбором входных параметров (`CustomParameterInspectorCell`), который классифицирует ответ кандидата и автоматически вызывает профильные инструменты `@tool`.
3. Реализовать условное ветвление пайплайна через `RunnableBranch` в зависимости от класса ответа, тональности (`sentiment`) и уровня знаний кандидата.
4. Оформить прикладные функции собеседования через декоратор `@tool` (`langchain_core.tools`) с типизацией и документацией.

---

## 2. Архитектура решения и используемый стек
* **Фреймворк:** `LangChain 1.4+` (`langchain-core`, `langchain-openai`, `pydantic`).
* **Локальный инференс:** `llama-server` (OpenAI-совместимый API, Apple M1, Metal GPU).
* **Файлы лабораторной работы:**
  * `interview_agent_v3.py` — исполняемый скрипт агента v3.0 (с поддержкой интерактивного режима и авто-демонстрации `--demo`).
  * `memory_v3.json` — хранилище профиля, банка разноуровневых вопросов, буферного окна и сводки диалога.
  * `LAB_03_CONCLUSIONS.md` — отчет о результатах работы.

### Схема конвейера LCEL с ветвлением и инструментами
```text
Входные параметры (вопрос + ответ кандидата)
   │
   ▼
CustomParameterInspectorCell (разбор параметров + Pydantic-классификатор)
   ├── Если has_code == True      ──► вызов @tool check_python_syntax (AST-анализ кода)
   ├── Если intent == "ask_hint"  ──► вызов @tool get_topic_hint (поиск подсказки)
   └── Загрузка контекста из HybridFileMemory (Window k=2 + Summary + Facts)
   │
   ▼
RunnableBranch (Условная маршрутизация по 5 веткам)
   ├─► [1. Негатив / Усталость] ──► empathy_prompt (поддержка + снижение нагрузки)
   ├─► [2. Запрос подсказки]    ──► hint_prompt (выдача наводки без штрафа по баллам)
   ├─► [3. Уровень == SENIOR]   ──► senior_eval_prompt (строгая архитектурная оценка)
   ├─► [4. Уровень == JUNIOR]   ──► junior_eval_prompt (обучающий разбор базы)
   └─► [5. По умолчанию MIDDLE] ──► middle_eval_prompt (стандартная оценка Middle)
   │
   ▼
CustomServiceOutputCell (Изолированная сервисная CELL вывода)
   ├── Вызов @tool record_score_and_adapt_level (запись в memory_v3.json + пересчет уровня)
   ├── Обновление InterviewBufferWindowMemory (k=2) и InterviewSummaryMemory (LLM)
   └── Визуальный рендеринг сервисного блока отдельно от реплики интервьюера
```

## 3. Многоуровневая система памяти (Занятие 04)
В третьей версии агента объединены три механизма памяти, дополняющие друг друга:

1. **Оконная память (`InterviewBufferWindowMemory`, $k=2$):**
   * Построена поверх `InMemoryChatMessageHistory` (`langchain_core.chat_history`).
   * Хранит дословно только последние $k=2$ обмена репликами («Кандидат — Интервьюер»). Это позволяет модели удерживать локальный контекст беседы без переполнения окна токенов.
2. **Суммаризирующая память (`InterviewSummaryMemory`):**
   * После каждого шага сжимает историю собеседования в краткую сводку из 2–3 предложений с помощью отдельной цепочки LLM.
   * Позволяет агенту помнить общую картину интервью даже после десятков вопросов.
3. **Файловая память фактов и уровня (`HybridFileMemory` $\to$ `memory_v3.json`):**
   * Хранит профиль кандидата, список завершенных вопросов с оценками и **текущий адаптивный уровень знаний** (`junior`, `middle`, `senior`).
   * Все три слоя синхронизируются на диск в `memory_v3.json` и восстанавливаются при перезапуске.

## 4. Инструменты `@tool` и разбор параметров (Занятие 05)
В соответствии с материалами Занятия 05 все прикладные операции оформлены через декоратор `@tool` с аннотациями типов и описаниями (docstring), по которым формируется JSON Schema аргументов:

| Инструмент (`@tool`) | Назначение | Когда вызывается |
| :--- | :--- | :--- |
| `fetch_question_by_level(level)` | Выбирает следующий непройденный вопрос из `memory_v3.json` под текущий уровень кандидата (`junior` / `middle` / `senior`). | Перед подачей нового вопроса кандидату. |
| `get_topic_hint(question_id)` | Извлекает методическую подсказку по текущему вопросу из базы. | Автоматически внутри `CustomParameterInspectorCell`, если `intent == "ask_hint"`. |
| `check_python_syntax(code)` | Проверяет код кандидата через модуль `ast.parse`, выявляя синтаксические ошибки и конструкции (`def`, `class`, `try/except`). | Автоматически внутри `CustomParameterInspectorCell`, если `has_code == True`. |
| `record_score_and_adapt_level(...)` | Сохраняет оценку в файл и динамически повышает/понижает уровень кандидата. | Внутри `CustomServiceOutputCell` после оценки технического ответа. |

Также в модуле реализован универсальный диспетчер `run_tools_as_messages(ai_msg)`, преобразующий `AIMessage.tool_calls` в список объектов `ToolMessage` для обратной подачи в модель.

## 5. Классификация и условное ветвление (`RunnableBranch`)
Для принятия решения о маршруте используется паттерн из Занятия 04: **«Классифицируй $\to$ Структурируй $\to$ Направь $\to$ Выполни»**.

1. **Структурированная классификация (`CandidateInputSchema` + `PydanticOutputParser`):**
   * Определяет намерение (`intent`: `technical_answer`, `ask_hint`, `negative_or_tired`), тональность (`sentiment`: `positive`, `neutral`, `negative`) и флаг наличия кода (`has_code`).
   * Для надежной работы на компактных локальных моделях (3B параметров) LLM-классификатор дополнен детерминированной страховкой, исключающей падение пайплайна при невалидном JSON.
2. **Логика ветвления `RunnableBranch`:**
   * **Если кандидат устал или выражает негатив (`negative_or_tired` / `sentiment == "negative"`):** активируется ветка `empathy_negative_branch`. Интервьюер поддерживает кандидата, дает мягкую наводку и при необходимости снижает уровень сложности с `senior` до `middle`.
   * **Если кандидат просит подсказку (`ask_hint`):** активируется ветка `hint_mentor_branch`. Агент передает кандидату результат работы инструмента `@tool get_topic_hint`. Оценка при этом не снижается, а вопрос остается активным для повторного ответа.
   * **Если дан технический ответ (`technical_answer`):** выбор ветки зависит от уровня кандидата в памяти (`junior_friendly_eval_branch`, `senior_strict_eval_branch` или ветка по умолчанию `middle_default_eval_branch`).
3. **Динамическая адаптация сложности вопросов:**
   * При высокой оценке ($\ge 8/10$) уровень кандидата повышается (`junior` $\to$ `middle` $\to$ `senior`), и следующий вопрос выбирается уже из пула более высокой сложности.
   * При низкой оценке ($\le 4/10$) уровень снижается, чтобы подобрать вопросы по силам кандидата.

## 6. Демонстрация работы (Сценарий `--demo`)
При запуске команды `python3 interview_agent_v3.py --demo` последовательно проверяются все ветки и инструменты:

1. **Шаг 1 (Запрос подсказки на вопросе про GIL, уровень Middle):**
   * Классификатор определяет `intent=ask_hint`.
   * Компонент параметров вызывает `@tool get_topic_hint`.
   * `RunnableBranch` выбирает ветку `hint_mentor_branch`. Вопрос остается активным без штрафа.
2. **Шаг 2 (Ответ с кодом Python на тот же вопрос про GIL):**
   * Классификатор определяет `intent=technical_answer`, `has_code=True`.
   * Автоматически срабатывает `@tool check_python_syntax` (подтверждает корректность AST: `функция 'worker'`, `блок try/except`, `оператор return`).
   * Срабатывает ветка оценки `middle_default_eval_branch`, выставляется высокая оценка (9/10).
   * Инструмент `@tool record_score_and_adapt_level` фиксирует ответ в `memory_v3.json` и **повышает уровень кандидата: `MIDDLE -> SENIOR`**.
3. **Шаг 3 (Следующий вопрос выбирается уже из пула `SENIOR` — про Event Loop в `asyncio`; кандидат пишет, что устал и вопрос слишком сложный):**
   * Классификатор фиксирует `intent=negative_or_tired`, `sentiment=negative`.
   * `RunnableBranch` переключается на ветку `empathy_negative_branch`.
   * Агент выражает поддержку, дает краткий ориентир и адаптирует уровень обратно до комфортного `MIDDLE`.

## 7. Сравнение версий агента (Лабораторная 2 vs Лабораторная 3)

| Критерий | Лабораторная №2 (v2.0) | Лабораторная №3 (v3.0) |
| :--- | :--- | :--- |
| **Архитектура цепочки** | Линейная цепочка LCEL (`prompt \| llm \| cell`) | Разветвленный граф с `RunnableBranch` (5 веток) |
| **Типы памяти** | Только файловая память фактов (`memory.json`) | Гибридная: `BufferWindow (k=2)` + `SummaryMemory` + `FileFacts` |
| **Подбор вопросов** | Фиксированная линейная очередь | Адаптивный выбор по уровню (`Junior` / `Middle` / `Senior`) |
| **Инструменты (Tools)** | Вшитые методы класса памяти | Полноценные `@tool` с типизацией и AST-анализом кода |
| **Реакция на эмоции и вопросы** | Любая реплика оценивалась по шкале 1–10 | Отдельные ветки для подсказок и эмоциональной поддержки |

## 8. Итоговые выводы
1. **Полнота охвата Занятий 04 и 05:** В агенте объединены оконная и суммаризирующая память, структурированная классификация через `PydanticOutputParser`, условная маршрутизация `RunnableBranch` и модульные инструменты `@tool`.
2. **Адаптивность собеседования:** Переход от плоского списка вопросов к динамическому уровню (`Junior` $\leftrightarrow$ `Middle` $\leftrightarrow$ `Senior`) и учету эмоционального состояния превратил скрипт из простого опросника в интерактивного собеседника.
3. **Устойчивость на локальных моделях:** Комбинация `PydanticOutputParser` с проверкой параметров в кастомном компоненте обеспечивает стабильную работу пайплайна на локальном сервере `llama-server` с моделями 3B параметров.
